# 1. 부하 분산 서비스
* 부하 분산(Load Balancing): 여러 서버나 시스템 자원에 작업이나 요청을 고르게 분배하여 성능 향상, 과부하 방지, 응답 속도 개선, 시스템 안정성 유지를 도모하는 기술
- 모든 사용자 요청이 **하나의 서버에 집중되지 않도록, 여러 대의 서버에 요청을 균등하게 혹은 효율적으로 분배하는 역할**

## 1.2 HTTP와 HTTPS
* http: 과거부터 사용하던 웹에서 데이터를 주고 받기 위한 통신 규약
* https: 보안(Secure)을 추가시켜 좀더 강화한 통신 규약
  - 사용자와 서버 간의 데이터를 암호화하여 도청이나 위조 방지
  - 개인 정보, 로그인 정보, 결제 정보 등을 안전하게 보호하는데 필수적인 기술
### HTTPS를 사용하는 이유
- **보안성과 신뢰성 때문**
- HTTP: 데이터를 평문(Plain Text)으로 전송하여, 네트워크 중간에서 누군가에 의하여 **데이터가 위조/변조될 수 있는 위험**
- HTTPS: **SSL/TLS 인증서 암호화를 통해 전송 데이터를 보호**해 주며, 인증서를 통해 서버의 신원을 검증하여 믿을 수 있는 사이트인지 확인해 줌.
-   SEO(검색 최적화) 측면에서 유리함

> SEO
>> 검색 엔진 최적화(Search Engine Optimization)는 웹사이트가 검색 엔진(Google, Naver, Bing 등)의 검색 결과에서 더 상위에 노출되도록 최적화하는 과정
>> "검색 엔진이 내 웹사이트를 잘 이해하고 신뢰할 수 있게 만들어 검색 결과 상단에 노출되도록 하는 전략"

## 1.3 로드 밸런서
- 로드밸런서: 각 요청을 뒷단 영역에 있는 **여러 서버에 적절하게 분산하여 전달하는 역할을 수행**

### 로드밸런서의 필요성
- 웹 페이지는 많은 사용자의 요청을 단일 서버가 처리하기 어려운 경우가 많기 때문에, 동일한 기능이나 정보를 가진 여러 대의 서버에 작업을 분산시켜 처리함으로써, 서버가 미응답 상태가 되거나 다운되는 상황을 미연에 방지할 수 있음
- 로드 밸런서: 분산 처리에서 **시스템의 부하를 효율적으로 관리하는 장치**

#### 장점
1. **과부하 방지**: 단일 서버가 모든 클라이언트 요청을 처리할 경우 순간적으로 트래픽이 몰리면 서버가 과부하에 걸리거나 다운될 수 있지만, 로드 밸런서는 요청을 여러 서버에 분산시켜 이러한 상황을 예방한다.
2. **처리 속도 향상**: 여러 서버가 병렬로 요청을 처리하면 전체 응답 속도가 빨라져 사용자 경험이 향상된다.
3. **서비스 안정성 향상**: 특정 서버에 장애가 발생하더라도 로드 밸런서는 정상적으로 동작하는 서버로만 요청을 분산하기 때문에, 사용자는 중단 없는 서비스를 제공받을 수 있다.
4. **확장성 확보 가능**: 서버 수를 필요에 따라 쉽게 추가하거나 제거할 수 있어, 트래픽 증가나 성능 요구에 유연하게 대응할 수 있다. 이러한 특성 때문에 로드 밸런서는 클라우드 환경과 매우 적합한 구조를 갖는다.

### 트래픽 분산 방식
- 어떻게 나누어 보낼 것인가를 결정하는 방식

#### 라운드 로빈(Round Robin)
- 가장 기본적인 분상 방식으로, **들어오는 요청을 서버에 순차적으로 분배해 주는 방식**
- 예를 들어 서버가 1,2,3 세 대 일 때 첫 번째 요청은 1, 두 번째 요청은 2, 세 번째 요청은 3, 네 번째 요청은 다시 1 순으로 순환 반복해 주는 방식
- 서버 성능이 비슷할 때 유용하며, 구현이 비교적 간단함

#### 가중 라운드 로빈(Weighted Round Robin)
- 각각의 서버에 **가중치(Weight)를 설정하여 성능이 더 좋은 서버에 더 많은 요청을 분배하는 방식**
- 예를 들어 1번 서버의 가중치가 2이고, 2번 서버의 가중치가 1이라고 가정했을 때, 요청 순서는 1, 1, 2,  다시 1 순으로 분배한다.
- 서버 간의 성능 차이가 있는 서버를 혼용할 때 적절히 사용할 수 있다.

#### 최소 연결 수(Least Connections)
- **현재 가장 적은 연결 숫자를 가진 서버에 요청을 분배하는 방식**
- 실시간 연결 수를 기준으로 판단하고, 요청 처리 시간이 불규칙하거나, 장시간 연결이 많은 환경에서 효과적

#### IP 해시(IP Hash)
- **클라이언트의 IP 주소를 해시하여 특정 서버에 고정 연결되도록 하는 방식**
- 세션 유지가 중요한 서비스(로그인 등)에 사용됨

### 로드 밸런서 종류별 차이점
AWS에서 제공하는 로드 밸런서는 크게 세 가지 유형으로 나뉜다.
- Classic Load Balancer: 가장 오래된 형태의 로드 밸런서로 네트워크 계층(Layer 4)과 애플리케이션 계층(Layer 7)을 모두 지원하지만 기능이 단순하고 제한적
  - 주로 과거의 **단순한 웹 서비스나 테스트 용도로 사용**됨
- Application Load Balancer: HTTP, HTTPS, gRPC와 같은 고급 애플리케이션 트래픽을 처리할 수 있도록 최적화된 로드 밸런서
  - 오직 애플리케이션 계층(Layer 7)만을 지원함
  - 경로 기반 또는 호스트 기반 라우팅이 가능하며, 마이크로서비스 아키텍처나 컨테이너 기반 서비스와 같은 **현대적인 웹 애플리케이션 환경에 적합**함.
  - Lambda 함수와의 연동도 지원해 서버리스 아키텍처에서도 유용하게 사용됨
- Network Load Balancer: 네트워크 계층(Layer 4)을 기반으로 하며, 매우 빠른 처리 속도와 낮은 지연 시간, 정적 IP 할당 기능 등을 제공함.
  - 수백만 개의 요청을 처리할 수 있는 초고성능 로드 밸런서로, 게임 서버나 실시간 통신, IoT, 금융 거래와 같은 **대량의 트래픽을 짧은 시간 안에 처리해야 하는 환경에 적합**함
 
**로드 밸런서 비교 표**

| 유형     | 사용 계층 | 특징       | 추천 상황         |
|-----------|-----------|-------------|-----------------|
| CLB(Classic Load Balancer) | L4 & L7 | 오래된 유형, 단순한 기능 | 레거시 환경, 간단한 서비스 |
| ALB(Application Load Balancer) | L7 | 웹 앱에 최적화, 고급 라우팅 지원 | 웹 서비스, 마이크로서비스 구조 |
| NLB(Network Load Balancer) | L4 | 초고속, 낮은 지연, 정적 IP 가능 | 게임, IoT, 금융, 대용량 처리 |

## 1.4 구성 요소
* AWS의 Elastic Load Balancer(ELB) 서비스를 구성하는 주요 요소

| 항목 |       설명               |
|------|--------------------------|
| 클라이언트(Client) | 웹 브라우저 또는 앱(App)             |
| 대상(Target)       | 요청에 대한 처리를 해주는 EC2 인스턴스 |
| 대상 그룹           | 수신 받은 트래픽을 보내고자 하는 대상들의 묶음 <br/> EC2 인스턴스, IP 주소 등을 묵어 놓은 그룹 |
| 로드 밸런서        | 대상 그룹에 있는 분산시켜 주는 분산 처리자 |
| 리스너(Listener)   | 수신 받은 요청을 대상 그룹으로 전달해주는 전달자 역할 <br/> 로드 밸런서가 수신하는 트래픽의 포트를 정의해 놓은 관리 장부 |
| 헬스 체크(Health Check) | 대상의 상태를 주기적으로 점검하는 절차 |

클라이언트는 인터넷을 통하여 로드 밸런서에게 요청을 전송하고, 로드 밸런서는 EC2 인스턴스 같은 대상으로 요청을 라우팅 한다.
로드 밸런서를 구성하기 위해서는 대상 그룹과 리스너가 필요하다.

### 대상 그룹
- 로드 밸런서가 트래픽을 분산할 때, 그 **트래픽을 전달 받을 대상을 모아 놓은 논리적 그룹**
- 헬스 체크 점검 대상의 최소 단위

### 리스너
- 구성해 놓은 **프로토콜 및 포트 번호를 사용하여 연결 요청을 확인해 주는 프로세스**
- 리스너에 정의한 규칙에 따라 로드 밸런서가 EC2 같은 대상으로 요청을 라우팅한다. OSI 7 Layer 계층 중 7에서 동작하는 ALB는 HTTP, HTTPS 프로토콜을 지원한다.
- HTTPS 프로토콜을 사용하는 경우 리스너에 SSL 서버 인증서르 ㄹ배포해야 한다.

- 정의 가능 규칙 예시
  - 특정 URL로 들어온 요청을 다른 URL로 리다이렉션 시킨다
  - http로 들어온 요청을 https로 리다이렉션 시킨다
  - 각각 대상 그룹별로 요청을 분산시킬 가중치 비율 지정

 ### 헬스 체크
 - 백엔드 서버(대상)가 정상적으로 작동하고 있는지 주기적으로 확인하는 절차
 - 정상 상태인 서버에만 트래픽을 전달함으로써, 장애가 발생한 서버로의 요청 방지
 - 헬스 체크는 대상 그룹을 대상으로 하여 설정하며, 실제 체크는 그 대상인 개별 인스턴스를 체크한다.
