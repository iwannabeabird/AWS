# 1. Terraform 소개
- 인프라 자동화(Infrastructure as Code, IaC): 운영자가 직접 콘솔에 접속해 서버를 생성하거나 네트워크를 연결하는 대신, 코드로 인프라를 정의하고 실행하여 동일한 결과를 얻을 수 있게 함

> 인프라
>> - 컴퓨터와 네트워크 환경에서 서비스를 운영하기 위해 필요한 기반 환경 전체
>> - 소프트웨어가 돌아가기 위해 필요한 하드웨어, 네트워크, 서버, 스토리지, 데이터베이스, 로드 밸런서, 보안설정 등 모든 것을 포함하는 개념
>> - Terraform은 이러한 인프라 자동화를 대표하는 도구 중 하나로, 여러 클라우드 서비스(AWS, Azure, GCP, OCI 등)를 HCL이라는 단일 언어로 제어할 수 있다.

## 1.1 인프라 자동화란?
- 서버, 네트워크, 스토리지, 보안 설정 등 IT 인프라를 사람이 수동으로 구성하지 않고 코드를 사용하여 관리하는 방식
- 이를 통해 반복 작업을 자동화하고, 일관성을 유지하며, 오류를 줄일 수 있다.
- 예를 들어 가상 머신 생성, 로드 밸런서 구성, 방화벽 규칙 설정 등이 있으며, 이러한 작업을 코드로 정의하고 실행함으로써 빠르고 신뢰성 높은 인프라 운영이 가능해진다.
- 인프라 자동화는 DevOps 문화의 핵심 요소 중 하나로, 개발과 운영의 경계를 허물고 협업을 촉진하는 기반이 된다.

> DevOps
>> 개발(Development)와 운영(Operations)의 경계를 허물고, 소프트웨어 개발과 시스템 운영 간의 협업과 자동화 및 지속적인 개선을 통해 빠르고 안정적인 서비스를 제공하기 위한 조직 문화를 의미한다.
>>

## 1.2 Terraform이란?
- Terraform: HashiCorp에서 개발한 오픈 소스 인프라 자동화 도구로, 코드 기반으로 클라우드 인프라를 정의하고 배포할 수 있도록 지원한다.
- 사용자는 HCL(HashiCorp Configuration Language)이라는 선언적 언어를 사용해 인프라 리소스를 기술하며, 이 코드를 통해 클라우드 리소스를 일관되게 생성, 수정, 삭제할 수 있다.
- AWS, Azure, Google Cloud, Oracle Cloud Infrastructure(OCI) 등 다양한 클라우드 서비스를 지원하므로, 멀티 클라우드 및 하이브리드 클라우드 환경에서도 강력한 도구이다.

## 1.3 Terraform의 장점
1. **인프라를 코드로 관리**할 수 있다. 인프라 구성을 코드화함으로써 버전 관리가 가능해지고, 여러 개발자 간 협업이 용이해지며, 구성 요소를 재사용 할 수 있다.
2. **플랫폼 독립성을 제공**한다. 다양한 클라우드 제공자와 연동할 수 있어 특정 벤더에 종속되지 않고, 필요에 따라 여러 환경에서 동일한 코드를 활용할 수 있다.
3. **선언적 구성**(Declarative Configuration): 사용자가 원하는 인프라 상태를 기술하면, Terraform이 현재 상태를 분석하여 필요한 변경만 자동으로 수행하므로 불필요한 수작업을 줄일 수 있다.
4. **계획과 적용의 분리 기능**을 통해 실행 전 변경 사항을 사전에 확인할 수 있어, 예기치 못한 리소스 변경이나 오류를 예방할 수 있다.
5. **모듈화 및 재사용성**을 제공하여 반복적으로 사용되는 리소스 구성을 모듈화하면, 다른 프로젝트에서도 손쉽게 재사용할 수 있어 효율적인 인프라 관리를 가능하게 한다.

## 1.4 Terraform 구성 요소
- Provider + Resource + Module + Variable = Terraform

### 프로바이더
- Terraform이 어떤 클라우드 환경 또는 인프라 플랫폼과 상호 작용할 지를 정의한다.
- 프로바이더는 Terraform이 각 플랫폼의 API를 호출해 리소스를 생성하거나 수정할 수 있도록 연결하는 역할을 한다.

### 리소스
-실제 인프라에서 생성되거나 관리되는 개별 단위
- ex. EC2 인스턴스, S3 버킷, VPC, 서브넷 등이 리소스로 표현된다.
'
### 모듈 
- 리소스들의 집합을 하나의 논리 단위로 묶음 구성
- 공통된 인프라 구성(VPC, 서브넷 세트 등)을 모듈로 정의해 두면, 여러 프로젝트에서 재사용할 수 있어 코드의 중복을 줄이고 유지 보수를 용이하게 한다.

### 베리어블
- Terraform 코드에서 값을 동적으로 처리할 수 있도록 도와 주는 요소
- 하드 코딩을 피하고 다양한 환경에 맞게 설정값을 바꿀 수 있도록 하기 위해 사용
- 리전(region), 인스턴스 타입(instance type), 태그(tag) 등을 변수로 지정하여 코드의 유연성을 높인다.

## 3.1 인증 키 자격 증명 생성
- Terraform이 AWS, OCI 같은 클라우드 환경에 접근하려면 **"내가 누구인지" 증명할 수 있는 인증 자격 증명(credentials)이 필요**하다.
 Terraform이 자동으로 클라우드 API를 호출하려면 접근 권한이 담긴 키 정보가 필요하다. 이 키는 일종의 API 전용 아이디/비밀번호 쌍이라고 이해할 수 있다.

### 인증 키 자격 증명 발급
- IAM > 사용자 생성 > 권한 부여 > 액세스 키 발급 > 키 등록 후 사용
- IAM: AWS 리소스 접근 권한을 제어하는 서비스로, 사용자 생성, 권한 관리, 액세스 키 발급 등을 수행함

## 3.3 HCL(HashiCorp Configuration Language)
- 인프라를 정의하기 위해 최적화된 도메인 특화 언어(DSL, Domain-Specific Language)
- Terraform의 핵심 언어로서, "사람이 읽기 쉽고, 기계도 실행 가능한 선언적 문법"으로 되어 있다.

### HCL이란
- HashiCorp사가 만든 구성(Configuration) 언어
- Terraform을 비롯해 Consul, Vault,Nomad 등 여러 HashiCorp 도구에서 사용되는 언어
- 인프라를 코드(IaC, Infra structure as Code)로 선언적으로 정의하기 위하여 만들어짐
- 사람이 읽기 쉬운 구조적 언어이면서도 기계가 파싱하기에도 적합하게 설계됨

### HCL의 주요 특징
사람이 읽기 쉽고, JSON처럼 구조화된 구성을 갖고 있다. 확장자는 ".tf" 형식으로 작성하면 된다.

#### 선언형 언어
- 절차를 지정하지 않고 최종적인 상태를 기술하는 방식. 즉, "무엇을 만들 것인가"에 초점을 둔다.
- ex) 다음과 같이 EC2 인스턴스 생성을 위한 구문만 정의해 놓으면, Terraform이 그 과정을 자동으로 처리해 줌.
```
resource "aws_instance" "example" {
  ami   = "ami-12345678"
  instance_type = "t2.micro"
}
```

#### 블록 구조 기반
- 중괄호 기호를 사용하여 block {...} 형태로 자원을 정의한다.
- 대표적인 블록 유형으로는 어떤 클라우드/플랫폼을 사용할지 설정하는 provider, AWS, Azure, GCP 등 클라우드 리소스를 정의하는 용도의 리소스가 있다.
- 이외, 변수 선언을 위한 variable, 실행 후 출력할 값을 지정하기 위한 output, 코드 재사용 단위인 module 등이 존재한다.

#### 키-값 쌍
- 각 블록의 내부는 'key=value' 형태로 속성을 지정한다.
- 사용 가능한 값은 문자열, 숫자, 불리언, 리스트, 맵 등 다양한 데이터 타입을 지원한다.
```
tags = {
  Name = 'MyInstance'
  Env = 'Dev'
```

#### 표현식(Expression) 지원
- 단순 값 뿐만 아니라, 다른 값 참조, 연산, 함수 호출 등이 가능하다.
- HCL v0.11까지는 '${}' 구문으로, v0.12 이후는 점(dot) 기호를 사용하여 직접 참조 가능하다.
```
instance_type = var.instance_type
subnet_id = aws_subnet.public_subnet.id
```

### HCL 사용 방법
#### 파일 확장자
- 'main.tf', 'variables.tf' 등과 같이 '.tf' 확장자를 주로 사용한다.
- JSON 형식도 '.tf.,json'으로 작성 가능하지만, 일반적으로 '.tf'를 선호한다.

#### 기본 구조 예시
중괄호 기호를 사용하여 블록 구조 기반 형식으로 사용한다.
```
provider "aws" {
  region = "ap-northeast-2"
}

resource "aws_instance" "myserver" {
  ami = "ami-0abcd1234abcd1234"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer"
  }
}

output "instance_ip" {
  value = aws_instance.myserver.public_ip
}
```

### HCL 장점
- 사람 친화적 (읽고 쓰기 쉬움)
- JSON 호환성(필요 시 변환 가능)
- 유연한 타입 시스템(string, list, map, object 등 지원)
- 표현식 지원(변수, 함수, 연산 가능)
- 모듈화 가능(코드 재사용, 구조화)
- 멀티 클라우드 지원(AWS, Azure, GCP 등과 함께 사용)

### 리소스 생성 문법
- 리소스: 실제 인프라에서 생성되거나 관리되는 개별적인 단위
  - EC2 인스턴스, S3 버킷, VPC, 서브넷 등이 리소스로 표현될 수 있음
- 각각의 리소스 항목들은 자신의 고유한 이름과 속성을 가지며, Terraform 코드를 통해 설정이 가능하다.

- 리소스를 생성하는 문법은 다음과 같다
  - `resource resource_type resource_name`
    - resource_type: 생성하고자 하는 리소스 유형을 정의하는 역할을 하며 erraform이 미리 정의해 놓은 문자열을 사용하면 된다.
    - resource_name: Terraform 내부에서 참조하고자 하는 이름으로 사용자가 자유롭게 지정할 수 있다.

* 이번 예시에서 사용되는 리소스 유형 목록

| 항목     | 설명                         |
|----------|-------------------------------|
| aws_vpc | VPC 리소스 |
| aws_subnet | 서브넷 리소스 |
| aws_internet_gateway | 인터넷 게이트웨이 |
| aws_route_table | 라우팅 테이블 |
| aws_route_table_association | 서브넷과 라우팅 테이블 연결을 정의하는 리소스 |
| aws_security_group | 보안 그룹을 위한 리소스 |
| aws_instance | EC2 인스턴스를 위한 리소스 |
| aws_eip | 탄력적인 IP 리소스 |
| aws_eip_association | EC2 인스턴스와 탄력적 IP를 연결(매핑 작업)하기 위한 리소스 |

* ex) 서브넷 "trf_public_sbn_2a"를 생성하는 구문
```
resource "aws_subnet" "trf_public_sbn_2a" {
  vpc_id = aws_vpc.trf_vpc.id
  cidr_block = "10.250.1.0/24"
  map_public_ip_on_launch = true
  availability_zone = "ap-northeast-2a"

  tags = {
    Name = "TRF-PUBLIC-SBN-2A" # 서브넷 이름
  }
}
```

## 3.4 Terraform 설정 파일 작성하기
* 실습용 VPC 구성을 위한 서브넷, 인터넷 게이트웨이 및 라우팅 테이블, 그리고 보안 그룹을 생성하기 위한 요약표

| Resource 유형 | 이름 | CIDR or 설명 | 가용 영역 |
|----------------|------|------------------|-------------------|
| VPC | TRF-VPC | 10.250.0.0/16 | 전체 |
| 서브넷 | TRF-PUBLIC-SBN-2A | 10.250.1.0/24 | ap-northeast-2a |
| 서브넷 | TRF-PUBLIC-SBN-2C | 10.250.11.0/24 | ap-northeast-2c |
| 인터넷 게이트웨이 | TRF-IGW | 인터넷 연결 | |
| 라우팅 테이블 | TRF-PUBLIC-RT | IGW 경로 연결 | |
| 보안 그룹 | TRF-PUBLIC-SG-2A | 80, 443, 22 허용 | |
| 보안 그룹 | TRF-PUBLIC-SG-2C | 80, 443, 22 허용 | |

### 프로바이더 지정

```
provider "aws" {
  region = "ap-northeast-2" # 서울 리전
}
```

- 프로바이더: Terraform이 어떤 클라우드 환경과 상호 작용할지를 정의하는 영역
- region: 리소스를 만들 리전을 지정하는 항목


### VPC 리소스

| 속성 목록 | 설명 |
|--------------|----------------------------------------------| 
| cidr_block | 네트워크 대역(CIDR Block) 지정 |
| enable_dns_support | DNS 지원 여부(DNS 사용 시 반드시 true) |
| enable_dns_hostnames | DNS 호스트 네임 할당 여부(true이면 EC2에 자동으로 DNS 이름이 만들어짐) |
| tags={...} | 리소스에 붙이는 태그로, 키-값 구조로 작성 |

```
# 1. VPC
# resource "resource_type" "resource_name"
resource "aws_vpc" "trf_vpc" {
  cidr_block = "10.250.0.0/16"
  enable_dns_support = true
  enable_dns_hostnames = true
  tags = {
    Name = "TRF-VPC"
  }
}
```

- 서울 리전에 ip 대역 10.250.0.0/16을 가진 VPC 생성
- 리소스 이름 "trf_vpc"은 다른 리소스에서 aws_vpc.trf_vpc.id의 형식으로 참조하여 사용할 수 있다.
- DNS 지원과 퍼블릭 호스트 네임을 활성화하며, 이름 태그를 "TRF-VPC"로 붙이겠다는 의미

### 서브넷 리소스

| 속성 목록 | 설명 |
|--------------|----------------------------------------------| 
| vpc_id | 서브넷이 속하는 VPC의 ID 지정 |
| cidr_block | 네트워크 대역(CIDR Block) 지정 |
| map_public_ip_on_launch | true이면 EC2에 자동으로 퍼블릭 IP를 할당함 |
| availability_zone | 서브넷이 배치되는 가용 영역(Availability Zone, AZ) 지정 |
| tags = {...} | 리소스에 붙이는 태그로, 키-값 구조로 작성 |

```
# 2. Subnet(공용)
resource "aws_subnet" "trf_public_sbn_2a" {
  vpc_id   =  aws_vpc.trf_vpc.id
  cidr_block = "10.250.1.0/24"
  map_public_ip_on_launch = true
  availability_zone = "ap-northeast-2a"

  tags = {
    Name = "TRF-PUBLIC-SBN-2A" # 서브넷 이름
  }
}
```

- trf_vpc 안에, 10.250.1.0/24 IP 대역을 가진 퍼블릭 서브넷을, ap-northeast-2a 가용 영역(AZ)에 생성
- 인스턴스를 띄울 때 자동으로 퍼블릭 IP를 부여
- 태그 이름을 "TRF-PUBLIC-SBN-2A"로 설정

```

### 보안 그룹 리소스
- 보안 그룹(Security Group, SG): 가상 방화벽 역할
- 인스턴스 단위로 만들어질 수 있으며 인바운드(ingress)와 아웃바운드(egress) 트래픽 규칙을 지정할 수 있다.

| 속성 목록 | 설명 |
|--------------|----------------------------------------------| 
| name | 보안 그룹 이름 |
| description | 보안 그룹의 세부 설명 작성 |
| vpc_id | 보안 그룹이 속하는 VPC ID 지정 |
| ingress | 인바운드 트래픽 허용 규칙 지정 |
| egress | 아웃 트래픽 허용 규칙 지정 |

* ingress 속성과 egress 속성들의 하위 속성이 가질 수 있는 목록

| 속성 목록 | 설명 |
|--------------|----------------------------------------------| 
| description | 인/아웃바운드 규칙에 대한 상세 설명 작성 |
| from_port | 시작 포트 번호 |
| to_port | 끝 포트 번호 |
| protocol | 허용할 프로토콜 지정(ex. SSH는 TCP 기반이므로 "tcp" 사용) |
| cidr_blocks | 허용하고자 하는 네트워크 대역(CIDR Block) 지정 |

```
# 6. Security Group(SSH 허용)
resource "aws_security_group" "trf_public_sg_2a" {
  name = "ALLOW-SSH-2A"
  description = "Allow SSH inbound traffic"
  vpc_id = aws_vpc.trf_vpc.id

  ingress {
    description = "SSH from anywhere"
    from_port = 22
    to_port = 22
    protocol = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound traffic"
    from_port = 0
    to_port = 0
    protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "TRF-PUBLIC-SG-2A"
  }
}

resource "aws_security_group" "trf_public_sg_2c" {
  name = "ALLOW-SSH-2C"
  description = "Allow SSH inbound traffic"
  vpc_id = aws_vpc.trf_vpc.id

  ingress {
    description = "SSH from anywhere"
    from_port = 22
    to_port = 22
    protocol = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Allow all outbound traffic"
    from_port = 0
    to_port = 0
    protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "TRF-PUBLIC-SG-2C"
  }
}
```
- ap-northeast-2a와 ap-northeast-2c 두 개의 가용 영역(AZ)에 각각 SSH 허용 보안 그룹을 만듦
- 각 보안 그룹은 SSH(22번 포트) 인바운드를 허용하고 모든 항목에 대한 아웃바운드를 허용한다.
- 이름으로 차이를 두어 가용 영역(AZ)을 구분함

### 인스턴스 리소스

| 속성 목록 | 설명 |
|--------------|----------------------------------------------|

| 속성 목록 | 설명 |
|--------------|----------------------------------------------| 
| instance_id | EC2 인스턴스 ID 지정 |

```

  domain = "vpc"

  domain = "vpc"

  allocation_id = aws_eip.trf_eip_2c.id

- VPC 기반의 인스턴스에 연결하는 경우 반드시 "vpc"라고 지정해야 함
- aws_eip 리소스를 사용하여 탄력적 IP를 생성할 수 있으며 VPC 내부에서 사용할 탄력적 IP를 생성하기 위하여 domain = "vpc"라고 작성함
- aws_eip_association": 탄력적 IP와 EC2 인스턴스 매핑
  - instance_id: 사용하고자 하는 EC2 인스턴스 ID 작성
  - allocation_id: 탄력적 IP의 ID를 작성하여 연걸
 
## 3.5 인프라 자동화 실습
- .tf 파일 작성 단계에서 HCL(HashiCorp Configuration Language) 문법을 사용하여 생성할 리소스와 설정을 정의한다.
- `terraform init` 명령을 실행하여 현재 디렉터리를 Terraform 작업 디렉터리로 초기화하고, 필요한 프로바이더(provider)를 다운로드한다. 이를 통해 Terraform이 클라우드 환경과 연동할 준비를 갖추게 된다.
- `terraform plan` 명령을 사용하여 실제로 인프라를 적용하기 전에 어떤 리소스가 생성, 변경, 삭제될지 미리 확인한다. 이는 사전 점검의 개념으로, 계획 내용을 검토하고 필요한 경우 옵션 '-out=파일이름'을 사용하여 계획 내용을 바이너리 파일로 저장할 수 있다.
- `terraform apply` 명령을 통해 작성한 설정 파일을 기반으로 실제 클라우드 환경에 리소스를 생성하고 적용한다. 이 단계에서 정의한 인프라가 실제로 배포된다.
- 실습 후에는 `terraform destroy` 명령을 사용하여 코드에 정의된 모든 라소스를 삭제할 수 있다. 특정 리소스만 삭제하고 싶을 때는 'terraform destroy -target=some_resource'와 같이 옵션을 지정할 수 있다.
