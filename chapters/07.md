# 1. 자원 삭제의 중요성
미사용 자원은 다음과 같은 문제를 유발한다.
- 불필요한 요금 발생: 사용하지 않아도 계속 과금되는 구조
- 보안 취약점 노출: 외부 접근이 가능한 자원이 남아 있을 가능성
- 운영 복잡도 증가: 콘솔이 복잡해지고 실수 위험 증가

자원을 단순히 생성하고 사용하는데 그치지 않고, 종료 후에는 반드시 삭제 및 정리하는 습관이 필요하다.
이는 단순한 청소 차원을 넘어, 비용 최적화, 보안 강화, 운영 효율 향상이라는 세 가지 측면에서 매우 중요한 클라우드 관리 전략이다.

## 1.1 비용 절감과 자원 관리
AWS에서 생성한 거의 대부분의 자원은 사용 여부와 관계없이 계속 과금이 발생한다.

### 인스턴스 중지
인스턴스를 중지하더라도 연결된 EBS(Elastic Block Store) 볼륨은 계속해서 요금이 부과된다.
**과금되지 않으려면 완전히 삭제(terminate)해야 한다.

### 미사용 탄력적 IP 해제
탄력적 IP(Elastic IP)는 **EC2 인스턴스에 연결되지 않은 상태에서는 과금**이 된다. 즉, IP를 할당만 하고 사용하지 않을 경우에도 비용이 발생하므로, 필요하지 않은 경우에는 반드시 해제하는 것이 좋다.

## RDS(Relational Database Service) 인스턴스
실제로 사용하지 않더라도, 인스턴스와 연결된 **스토리지, 자동 백업, 스냅샷 등의 리소스만큼 요금이 계쏙 부과**된다.

## 1.2 보안 및 관리 효율성 향상
### 퍼블릿 S3 버킷
S3 버킷은 데이터를 저장하는 최상위 컨테이너(저장소 단위)를 의미하며 파일을 보관하는 '폴더'나 '드라이브'와 같은 개념이다.
기본적으로 비공개(private) 상태로 생성되지만, 설정에 따라 공개(public) 접근이 가능하도록 변경될 수 있다. 이 경우 버킷 내부에 저장된 파일이 누구에게나 인터넷을 통해 열람 가능해지며, 다음과 같은 문제가 발생한다.
- 고객 개인 정보, 영업 비밀, 내부 문서 등 민감한 정보 유출
- 해커가 버킷을 스캔하여 파일을 무단 다운로드하거나 악성 파일을 업로드
- 검색 엔진에 S3 URL이 노출될 경우, 예기치 않은 공개 상태 지속

이를 위해서 사용이 끝난 S3 버킷은 반드시 삭제하고, 퍼블릭 접근 설정은 버킷 생성 시부터 제한한다. 또한 AWS S3 퍼블릭 액세스 차단(Bucket Policy, ACL 설정 포함)을 활용한다.

### IAM 사용자, 그룹, 역할의 권한 방치
IAM은 AWS 내 모든 자원 접근 권한을 제어하는 중심 시스템이다. 하지만 다음과 같은 상황이 발생하면 심각한 보안 사고로 이어질 수 있다.
- 퇴사한 직원의 IAM 사용자 계정이 삭제되지 않고 남아 있음
- 임시 테스트용으로 만든 IAM 역할이 남아 있어 외부 애플리케이션이 계속 접근
- 과도한 권한(AdministratorAccess)을 가진 역할이나 사용자 계정이 비활성화 없이 유지됨

- 이를 위해서 IAM 사용자나 역할은 마지막 사용일 기준으로 정기적으로 점검을 하고, 미사용 계정은 즉시 삭제하거나 비활성화한다. 또한 CloudTrail을 통해 IAM 권한 오남용을 감시할 수 있다.
- CloudTrail 서비스는 AWS 내에서 벌어지는 활동을 기록하고 추적, 기록해 주는 감사(audit) 및 추적(logging) 서비스이다.

### Lambda 함수, API 게이트웨이, EC2 키 페어 등 장기 미사용 리소스
사용자가 잠깐 테스트 용도로 만든 Lambda 함수나 API 게이트웨이가 인터넷에 노출된 상태로 장시간 방치가 되면 다음과 같은 문제점이 발생할 수 있다.
- 외부 공격자가 해당 엔드 포인트(URL)를 무차별적으로 호출하여 리소스 낭비 또는 데이터 손상
- 함수 내부에 하드 코딩된 민감 정보(API 키, DB 암호 등)가 노출될 위험
- EC2 키 페어가 노출된 상태로 존재하면, EC2에 무단 접근 시도 가능성 증가

이를 위해서 AWS Lambda, API 게이트웨이, EC2 키 페어 등의 마지막 수정일 기준으로 사용 여부를 정기적으로 점검하고, 불필요한 리소스는 삭제한다.

### 정기적인 자원 관리
정기적인 자원 정리가 주는 효과로는 다음과 같다.
| 항목 | 설명 |
|----------------|--------------------------------------|
| 보안 리스크 감소 | 외부 접근 경로 최소화, 권한 통제 강화 |
| 관리 효율성 향상 | 리소스 구조가 단순화되어 운영 부담 감소 |
| 사고 예방       | 실수로 인한 삭제나 누락 방지, 불필요한 알림과 로그 감소 |

클라우드 보안은 무언가를 만드는 일보다, 쓰고 나서 정리하는 습관이 훨씬 중요하다.

## 1.3 자원 삭제 시 주의 사항
### 의존성 확인
**EC2 인스턴스를 삭제할 경우 연결된 EBS 볼륨, 탄력적 IP, 보안 그룹 등 관련 자원도 함께 정리**해야 하며, CloudFormation이나 Terraform과 같은 IaC(Infrastructure as Code) 도구를 사용했다면 전체 스택 삭제를 통해 일괄적으로 정리할 수 있다.

### 백업 여부 확인
**삭제 전에 스냅샷, AMI, S3 백업 등을 생성하여 향후 복원 가능성을 확보**해야 한다.
특히, RDS, EFS, DynamoDB와 같은 데이터베이스 및 파일 시스템 서비스는 데이터 손실을 방지하기 위해 반드시 백업을 수행해야 한다.

### 삭제 불가한 자원
기본 보안 그룹, VPC, 기본 키 페어 등은 일반적으로 삭제할 수 없거나, **삭제하려면 먼저 연결을 해제**해야 한다.

### 리전별 자원 확인
AWS 자원은 리전 단위로 생성 및 관리되므로, 특정 리전에서 EC2를 종료했더라도 다른 리전에 남아 있는 자원이 있을 수 있으므로 **모든 리전을 점검**해야 한다.

### 예상치 못한 서비스 영향 방지
특히 프로덕션 환경에서 자원을 삭제하기 전에 서비스 영향도를 분석하고, 삭제로 인해 발생할 수 있는 문제를 사전에 점검해야 한다. 모니터링 설정이나 알림 구독 상태 또한 확인하여 서비스 중단이나 데이터 손실을 예방할 수 있다.

# 2. AWS 관리 콘솔을 통한 자원 삭제
AWS 자원은 임의의 순서로 삭제할 수 없으며, 자원 간의 상호 연관성을 고려하여 올바른 순서로 삭제해야 한다.
** 자원 삭제 순서**
Elastic IP -> EC2 Instance -> Load Balancer -> Target Group -> RDS -> Security Group -> VPC -> DHCP Option -> ACM -> Hosted Zone

## 2.1 탄력적 IP
탄력적 IP(Elastic IP, EIP)를 관리할 때 삭제보다는 **소유권 반환**이라는 개념이 더 정확하다. 탄력적 IP는 사용자가 AWS 계정 내에서 소유하고 관리하는 고정 공인 IP이기 때문에, 단순히 삭제하는 것이 아니라 먼저 IP와 연결된 자원을 해제하고,
이후 소유권을 AWS로 반환하는 절차를 거친다.

### 연결 해제
특정 EC2 인스턴스나 네트워크 인터페이스에 연결되어 있는 탄력적 IP를 분리한다. 이때 주의할 점은 연결을 해제한다고 해서 EIP가 바로 삭제되는 것이 아니라, **여전히 사용자의 AWS 계정 내에서 보유된 상태로 남아 있다는 점**이다.
즉, 연결 해제는 IP를 특정 인스턴스와 분리하는 작업이며, 이후 재사용하거나 다른 인스턴스에 연결할 수 있다.

### 릴리스(Release)
사용자가 소유하고 있는 탄력적 IP의 **소유권을 포기하고, AWS로 반환**한다. 릴리스를 수행하기 전에, 해당 IP가 연결되어 있는 리소스가 없는지 반드시 확인해야 하며, **릴리스 이후에는 해당 IP를 다시 되찾을 수 없다는 점**을 주의해야 한다.

### 탄력적 IP 주소 연결 해제
현재 EC2 인스턴스나 네트워크 인터페이스에 연결되어 있는 탄력적 IP 주소를 분리하는 작업이다.
* 사용 시점
   - 인스턴스를 종료하거나 재배치하기 전에 IP를 보존하고자 할 때
   - 탄력적 IP를 다른 인스턴스에 재사용하고 싶을 때
   - IP 주소를 일시적으로 분리하고 싶을 때
* 삭제 효과
  - IP 주소는 보존이 되며, 사용자의 AWS 계정에 여전히 소유 상태로 남는다.
  - 연결이 되어 있지 않은 유휴 상태의 탄력적 IP는 요금이 부과된다.

### 탄력적 IP 주소 릴리스
AWS에서 "탄력적 IP 주소 삭제(Delete)"라는 용어는 존재하지 않는다. 실제로는 릴리스(Release)를 의미한다. 즉, 자신의 AWS 계정에서 탄력적 IP 주소 소유권을 가지고 있었는데 이를 AWS Pool로 반환하는 의미이다.
* 사용 시점
  - 해당 IP를 더 이상 사용하지 않을 때
  - 불필요하게 사용 중인 IP 주소를 정리하고 싶을 때
  - 유휴 상태의 IP에 대해 발생하는 비용을 줄이고 싶을 때
* 주의 사항
  - 릴리스한 IP 주소는 다시 할당되지 않는다.
  - 동일한 같은 다른 사람이 할당 받을 수 있으므로 "이전 IP 주소를 다시 할당 받는다"는 보장이 없다.


## 2.2 EC2 인스턴스 종료(삭제)
EC2 인스턴스는 실행 중일 때 시간 단위로 과금된다. (Amazon Linux EC2 인스턴스는 초 단위로 과금되고, Windows Server EC2 인스턴스는 시간 단위로 요금 전체가 과금된다.)
예를 들어서 시간 단위 과금의 경우, 1시간 5분을 사용한다고 하더라도 2시간 기준 금액이 과금된다.
사용히 끝난 인스턴스는 반드시 "정지(Stop)" 또는 종료(Terminate)" 처리를 해야 한다. 

### 인스턴스 정지와 종료(삭제)
EC2 인스턴스를 정지하면 인스턴스를 잠시 중단시킬 수 있으며, 나중에 다시 시작할 수 있다. 다만, 이 경우 EBS(스토리지) 사용에 대해서 요금이 과금되며, 퍼블릭 IP가 변경될 수 있다. 
반면에 종료는 인스턴스를 완전히 삭제하는 작업이다. EBS를 포함한 모든 데이터와 정보가 삭제되며 복구가 불가능하다. 퍼블릭 IP도 함께 삭제되고, 추가 요금도 발생하지 않는다.

| 작업 이름 | 정지(Stop)       | 종료(Terminate) |
|-------------|-----------------------------|---------------------------------|
| 상태       | 인스턴스를 중지 후 재시작 가능 | 인스턴스를 완전히 삭제함           |
| 과금 여부  | EBS(스토리지)에 대해서는 과금됨 | 완전히 삭제되므로 과금 없음       |
| IP 주소   | 퍼블릭 IP가 변경될 수 있음     |  퍼블릭 IP 포함 모든 정보 삭제됨   |
| 복구 가능성 |  다시 시작하면 기존 상태로 복구됨 | 복구 불가능. 모든 데이터 삭제됨 |

## 2.3 로드 밸런서 삭제
### 삭제 체크 리스트
로드 밸런서 삭제 전 다음 항목들을 반드시 점검해야 한다.

| 작업 이름 |                  설명                     |
|------------|---------------------------------------------------------------------------------|
| 대상 그룹 | 로드 밸런서가 연결하고 있는 대상 그룹 |
| 리스너   | HTTPS 리스너의 경우 SSL 인증서를 반드시 점검해야 함 |
| EC2 인스턴스 | 로드 밸런서에서 EC2 인스턴스 연결 해제 필요 여부 확인 |
| 도메인 연결  | Route 53 또는 외부 DNS에서 로드 밸런서 주소를 사용 중인 경우, DNS 설정 변경 필요  |

### 삭제 후 후속 조치
- 로드 밸런서를 삭제한 이후 관련된 자원에 대해 몇 가지 후속 조치가 필요하다.
- 우선, 더이상 사용하지 않는 대상 그룹이 있다면 이를 함께 정리해 리소스 낭비를 줄여야 한다.
- 또한, 로드 밸런서에 연결되어 있던 Route 53 설정이 있다면, 도메인(DNS) 설정을 삭제하거나 필요한 경우 수정해야 한다.
- 마지막으로 로드 밸런서와 함께 사용되던 SSL 인증서가 있다면, 사용 중이던 인증서를 삭제하거나 추후 재사용 여부를 고려해 적절히 관리해야 한다.

## 2.4 대상 그룹 삭제
대상 그룹에 삭제되면, 해당 그룹으로 트래픽을 전달할 수 없게 되므로, 서비스 장애가 발생할 수 있다. 따라서 항상 대상 그룹 삭제 전에 대체 설정이 완료되었는지 확인해야 한다.

### 삭제 체크 리스트
- 먼저, **리스너와의 연결 여부**를 살펴야 한다. 대상 그룹이 리스너 규칙에 연결되어 있는 상태에서는 삭제가 불가능하며, 삭제를 위해서는 먼저 리스너 규칙에서 해당 대상 그룹을 제거해야 한다.
- 둘째, **대상 그룹 사용 여부**를 확인해야 한다. 로드 밸런서가 여전히 해당 대상 그룹을 사용하고 있다면, 삭제할 수 없다. 따라서 대상 그룹을 참조하고 있는 모든 연결 상태를 점검해야 한다.
- 마지막으로, **대체 대상 그룹 구성 여부**도 중요하다. 만약 삭제하려는 대상 그룹이 유일하게 설정되어 있는 경우, 삭제 후에는 트래픽이 전달되지 않을 수 있으므로 필요한 경우 대체 대상 그룹을 먼저 구성한 후 삭제해야 한다.
- 이렇게 해야 대상 그룹 삭제로 인한 서비스 중단을 방지할 수 있다.

## 2.5 RDS 삭제
### 삭제 시 주의 사항
RDS 인스턴스를 삭제할 때 몇 가지 중요한 사항을 반드시 고려해야 한다.
- 먼저, **복구가 불가능**하다는 점이다. 삭제된 RDS 인스턴스는 복구할 수 없으며, 최종 백업 없이 삭제하면 데이터가 완전히 손실된다. 따라서 중요한 데이터가 있다면 삭제 전에 반드시 백업해야 한다.
- 둘째, **자동 백업본 관리**이다. 운영 환경에서는 자동 백업을 삭제하지 않고 보관하는 것이 바람직하다. 자동 백업을 유지하면 추후 문제가 발생했을 때 데이터 복구에 활용할 수 있다.
- 셋째, **자동 삭제되지 않는 리소스**를 주의해야 한다. 보안 그룹이나 서브넷 그룹과 같은 일부 리소스는 RDS 인스턴스를 삭제하더라도 자동으로 제거되지 않으므로, 필요 없는 리소스는 직접 삭제하지 않으면 불필요한 과금이 발생할 수 있다.
- 마지막으로, **삭제 후 확인 사항**도 중요하다. 인스턴스 삭제 후 스냅샷이 남아 있으면 스토리지 비용이 계속 발생하며, CloudWatch 모니터링 항목이 남아 있을 수도 있으므로 이를 반드시 확인해야 한다.

### 삭제 옵션
데이터베이스 인스턴스를 삭제할 때는 몇 가지 중요한 설정을 확인해야 한다. 
- 먼저, **최종 스냅샷 생성 여부를 결정해야 한다.** 인스턴스를 삭제하기 전에 마지막 백업을 생성할지 선택할 수 있으며, 특히 프로덕션 환경에서는 이를 체크하여
안전하게 데이터를 보존하는 것이 권장된다.
- 다음으로, **자동 백업을 보존할지를 선택할 수 있다.** 삭제 과정에서 자동 백업과 수동으로 생성한 스냅샷을 함께 삭제할지를 결정하며, 이 옵션을 체크하면 모든 백업이 제거된다.
- 마지막으로, 삭제 확인을 위해 인스턴스 이름을 입력해야 한다. 인스턴스 삭제 의사를 명확히 하고 실수로 인한 삭제를 방지하기 위해, 사용자에게 인스턴스 이름을 직접 입력하도록 요구할 수 있다.

## 2.6 보안 그룹 삭제
EC2 인스턴스를 RDS와 연동시키면 EC2 인스턴스와 RDS 각각에 대한 보안 그룹이 자동으로 생성된다. 이 보안 그룹은 인바운드 규칙과 아웃바운드 규칙을 가지고 있다. 따라서 해당 보안 그룹들을 삭제하기 이전에 우선 **인바운드 규칙과 아웃바운드 규칙을 분리시켜야 한다.**

**보안 그룹 삭제 전 필요 작업**

| 항목 | 조치 내용 |
|--------|------------------------------|
| EC2 보안 그룹 | 인스턴스 연결 해제 + 아웃바운드 규칙 제거 |
| RDS 보안 그룹 | 인스턴스 연결 해제 + 인바운드 규칙 제거 |
| 보안 그룹 삭제 | 모든 연결 및 규칙 제거 후 삭제 가능 |

## 2.7 VPC 삭제
VPC는 여러 리소스를 연결할 수 있는 가상 네트워크를 생성하는 서비스로 VPC를 삭제하기 전에 어떤 항목들이 연결되어 있는지 확인하는 것이 중요하다.
- 먼저, 인터넷 게이트웨이(IGW)는 VPC에 연결되어 있다면, VPC 삭제 시 자동으로 함께 삭제된다.
- 마찬가지로, 라우팅 테이블도 VPC와 연동되어 있는 경우 VPC 삭제 시 자동으로 제거된다. 또한, 서브넷 역시 VPC 삭제와 함께 자동으로 삭제된다.
- 한편, EC2 인스턴스는 VPC에 연결된 상태라면 먼저 중지시키고 종료한 후 삭제해야 한다.
- 마지막으로, 보안 그룹은 기본 보안 그룹을 제외한 사용자 정의 보안 그룹만 삭제할 수 있으며, 인스턴스가 연결되어 있는 경우 먼저 연결을 해제해야 삭제가 가능하다.

## 2.8 DHCP 옵션 세트 삭제
DHCP 옵션 세트는 VPC 생성 시 자동으로 생성된다. 이 항목은 VPC에서 EC2 인스턴스에 자동으로 네트워크 정보를 할당하는데 사용되는 설정 모음이다.
기본(Default) DHCP 옵션 세트는 삭제가 불가능하며, 다른 VPC를 참조하고 있으면 역시 삭제가 불가능하다.

### DHCP 포함 정보
#### 포함된 정보
- 도메인 이름(Domain Name)
- DNS 서버 주소(Domain Name Server)
- NTP 서버(Network Time Protocol)
- NetBIOS 서버 등

## 2.9 인증서 삭제
클라우드 환경(AWS 등)이나 서버 운영 환경에서 사용되는 SSL/TLS 인증서는 일정 기간 동안 유효하며, 만료되거나 더 이상 사용하지 않을 경우 보안을 위해 삭제하는 것이 좋다. 현재 ELB, CloudFront, API 게이트웨이 등에 연결된 인증서를 삭제하는 경우 반드시 먼저 연결 해제를 해야 한다.

### 인증서 삭제의 필요성
인증서는 관리와 보안 측면에서 필요에 따라 삭제할 수 있다. 
- 먼저, 만료된 인증서는 제거하는 것이 좋다. 더 이상 유효하지 않은 인증서를 그대로 두면 관리가 복잡해지고, 실수로 재사용될 위험이 있기 때문이다.
- 또한, 보안 유지 측면에서도 인증서를 삭제하는 것이 중요하다. 인증서에는 민감한 정보가 포함될 수 있으므로, **더 이상 필요하지 않은 인증서를 제거함으로써 정보 노출 위험을 줄일 수 있다.**
- 마지막으로, 정리 및 최적화의 목적도 잇다. 사용하지 않는 인증서를 정리하면 리소스 관리가 용이해지고 시스템 구조가 보다 간결해진다.

### 삭제 시 유의사항
- 먼저, 자동 개신 대상인 인증서의 경우 주의가 필요하다. 예를 들어, Let's Encrypt와 같이 자동 갱신되는 인증서를 삭제할 때 관련 스크립트나 프로세스도 함께 정리해야 불필요한 오류가 발생하지 않는다.
- 다음으로, 의존성을 체크해야 한다. 인증서를 사용하는 리소스(로드 밸런서, CloudFront, API 게이트웨이 등)가 있다면, 먼저 해당 리소스에서 인증서를 제거한 후 삭제를 진행해야 시스템 장애를 방지할 수 있다.
- 마지막으로, 백업이 필요한지도 확인해야 한다. 나중에 인증서를 복구해야 할 가능성을 대비해 인증서 키를 별도로 백업해 두는 것이 좋다. 다만, 조직의 보안 정책에 따라 백업을 금지하는 경우도 있으므로, 이를 반드시 확인하고 절차를 따르는 것이 중요하다.
 
## 2.10 호스팅 영역 삭제
- AWS Route 53에서 호스팅 영역(Hosted Zone)을 삭제하려면, 단순히 "삭제" 버튼을 누르는 것만으로는 안 되고, 몇 가지 사전 정리 작업을 반드시 수행해야 한다.
- 삭제하려는 호스팅 영역이 여전히 DNS 트래픽을 처리하거나 AWS 리소스와 연결되어 있을 수 있기 때문이다.

### 레코드 삭제
레코드는 DNS 요청을 처리하는 실질적인 지시 사항이다. 예를 들어, 도메인을 특정 IP로 연결하거나 이메일 라우팅을 처리하는 것이 될 수 있다.
호스팅 영역을 삭제하기 전에, 사용자가 추가한 모든 레코드들을 삭제해야 한다.
* 호스팅 영역 생성 시 자동으로 생성되는 기본 레코드 (삭제하지 않아도 됨)
  - 'NS'(Name Server) 레코드
  - 'SOA'(Start of Authority) 레코드
* 호스팅 영역을 삭제하기 전에 우선 삭제해야 되는 레코드
  - A 레코드('www.example.com -> IP주소')
  - CNAME 레코드('www.example.com -> example.com')
  - MX 레코드(메일 서버)
  - TXT 레코드(도메인 인증용) 등
 
- 호스팅 삭제 이후, 해당 도메인에 대한 모든 DNS 설정이 사라지며, 웹사이트 연결 등도 중단된다. 그리고, 도메인을 다른 DNS 제공업체에서 계속 사용하려면, 그에 맞게 네임 서버의 정보를 갱신해 주어야 한다.
